# Stateless OpenAI-Wire Proxy Redesign

## Objective

Replace the current prompt protocol, dispatcher tool, event collector, and OpenCode-output reconstruction with a much smaller provider-proxy architecture.

OpenCode will be used only to:

- Resolve a configured and enabled `provider/model`.
- Apply provider configuration, API keys, OAuth, custom headers, base URLs, and model-specific options.
- Produce one final authenticated provider fetch template inside an isolated burner session.

The plugin will then make exactly one real inference request itself and expose its result through a stateless OpenAI Chat Completions API.

## Supported Contract

Public endpoints:

- `POST /v1/chat/completions`.
- `GET /v1/models`.
- `GET /v1/version` returning `{ object: 'version', plugin, opencode }`.

Public Chat Completions support:

- A complete message history on every request; no server-side conversation ID or retained state.
- `system`, `developer`, `user`, `assistant`, and `tool` messages.
- String content and ordered text/image content arrays.
- HTTP(S) image URLs and `data:image/...;base64,...` images; no OpenAI file IDs.
- Function tools, historical assistant tool calls, tool results, and parallel generated tool calls.
- Streaming and non-streaming output.
- Explicit provider reasoning output through the existing `reasoning_content` extension.
- One choice only. `tool_choice`, structured output, and the stateful OpenAI Responses API remain unsupported.

Supported **upstream** provider protocols in the first release:

- OpenAI Chat Completions wire format.
- OpenAI Responses wire format.

The plugin does not expose a Responses endpoint. OpenAI Responses is only an internal upstream adapter used when OpenCode selects that transport for a model.

Deferred upstream protocols:

- Gemini/Vertex.
- Anthropic Messages.
- Bedrock Converse/invoke.
- Native/custom transports that bypass `fetch`.

Only OpenCode AI SDK providers/models whose resolved request uses one of the supported OpenAI wire formats are advertised and accepted. Capture-time protocol detection remains authoritative and fails safely if metadata is stale or a custom provider behaves differently.

## Core Request Lifecycle

```text
OpenAI client
  -> validate Chat Completions request
  -> resolve model from effective supported model catalog
  -> register request-local capture context
  -> create disposable OpenCode session
  -> prompt it with a minimal sentinel and { '*': false }
       -> burner-only hooks erase OpenCode system instructions
       -> burner-only chat.headers adds opaque capture marker
       -> OpenCode/AI SDK prepares provider request and credentials
       -> global fetch interceptor sees final marked inference fetch
       -> capture URL/method/headers/body without network call
       -> return protocol-correct synthetic SSE completion to OpenCode
  -> abort if needed and always delete burner session
  -> select OpenAI Chat or Responses adapter from captured request
  -> replace sentinel conversation with caller messages/tools/images
  -> retain captured provider/model/static options and authentication
  -> perform exactly one real upstream streaming request
  -> normalize upstream events
  -> stream OpenAI chunks or aggregate one OpenAI JSON completion
```

The burner is not the inference session and its synthetic assistant output is discarded. Its only output is the authenticated request template.

OAuth/token refresh requests needed to prepare credentials may reach their authentication servers. The capture invariant is narrower and testable: the burner must make no request to the model inference endpoint and incur no model generation/billing.

## Capture Layer

### Installation and lifecycle

Add `src/proxy/capture.ts` with one process-wide, reference-counted wrapper around `globalThis.fetch`.

- Save the fetch function that exists when the first plugin instance initializes.
- Install one wrapper even if multiple plugin instances are loaded.
- Register each plugin instance with a capture manager; unregister it during `dispose`.
- Restore the saved fetch only when the final manager is disposed and only if the installed wrapper is still current, avoiding overwriting another plugin's later fetch change.
- Pass every unrecognized request through unchanged.
- Do not wrap `output.options.fetch` as the primary interception point because provider/OAuth fetch functions may add credentials after that layer. The global boundary is required to observe the final request.

### Correlation

Use a cryptographically random marker per capture attempt.

- Register `{ marker, sessionID, deferred, signal, deadline }` before prompting.
- In burner-scoped `chat.headers`, add a private header such as `x-opencode-openai-capture: <marker>`.
- At global fetch, parse `Request` and `RequestInit` forms and inspect headers case-insensitively.
- Match the marker to exactly one pending context.
- Remove the marker from the captured header set and from any forwarded request.
- Never use module globals such as `currentSessionID`, current body, current model, or current request.
- Reject duplicate inference captures for one marker rather than guessing which request is authoritative.
- Concurrent burners, identical models, retries, and authentication fetches must remain isolated.

### Capture classification and no-upstream response

At a marked fetch:

1. Materialize the final URL, method, headers, and JSON body without consuming a caller-owned stream irreversibly.
2. Require `POST`, a JSON body, and a recognizable OpenAI Chat (`messages`) or Responses (`input`) request shape/endpoint.
3. Store an immutable captured request after stripping the marker and hop-by-hop headers.
4. Resolve the request-local deferred before returning the synthetic response.
5. Return a protocol-correct synthetic SSE response directly; never call the saved fetch for this inference request.

Synthetic Chat stream:

- One assistant text delta containing a fixed sentinel-safe value.
- A normal `stop` finish chunk.
- `[DONE]`.

Synthetic Responses stream:

- Minimal valid response-created/output-item/content-part/text-delta/completed events expected by the pinned AI SDK.
- Stable synthetic IDs unrelated to the external response.

Keep these fixtures in tests and validate that OpenCode's prompt call settles. If OpenCode changes the expected event grammar, the smoke test should fail rather than allowing the capture request upstream.

### Failure behavior

- Capture timeout: abort and delete the burner, return `502 unsupported_provider`.
- Marker missing because a transport rebuilt/stripped headers: timeout and fail; do not fall back to sending a probe.
- Non-JSON, unknown protocol, multiple marked inference calls, or native transport: fail before the real request.
- Client cancellation during capture: unregister marker first, abort burner, delete session, return cancellation without leaving a late marker authorized.
- Never include captured secrets, full messages, or image data in logs/errors.

## Burner Session and Hooks

Replace the current `SessionRunner`, `EventHub`, and dispatcher coordination with a small capture runner in `src/proxy/runner.ts`.

Burner prompt properties:

- New session for every external request.
- Selected provider/model passed explicitly.
- One short sentinel text part only.
- Exact tools map `{ '*': false }`.
- No plugin tool registration.
- No external tool schemas or actual user messages sent through OpenCode.

Burner-only hooks in `src/plugin.ts`:

- `experimental.chat.system.transform`: replace `output.system` with `[]` for registered capture sessions only.
- `chat.headers`: inject the marker for registered capture sessions only.
- If needed after a real compatibility test, `experimental.chat.messages.transform` may reduce the burner model messages to the sentinel, but it must remain session-scoped and must not carry user content. Do not add it speculatively.

Normal TUI, desktop, and OpenCode server sessions must be unaffected. Remove `config`, `tool`, `tool.execute.before`, `tool.execute.after`, and event hooks once the old bridge is deleted.

Cleanup order for every capture attempt:

1. Remove marker/session authorization so late fetches cannot be captured.
2. Stop waiting for capture and detach cancellation listeners/timers.
3. Abort the burner if its prompt has not settled.
4. Always delete the burner in an independent bounded operation.
5. Observe late prompt rejection to avoid unhandled promises.

Plugin disposal marks the HTTP service draining, rejects new requests, aborts all capture and upstream controllers, waits a bounded grace period, stops the listener, unregisters capture state, and restores fetch when appropriate. Disposal remains idempotent.

## Captured Template Rewriting

Do not mutate and forward OpenCode's sentinel request blindly. Each adapter constructs a new body from an allowlisted set of captured static fields plus the normalized external request.

Preserve from capture where valid:

- Provider model ID and endpoint-selected model alias.
- Provider-specific options already selected by OpenCode, such as reasoning effort, service tier, safety-compatible options, cache options, and vendor extension fields.
- Required provider headers, authorization, URL query parameters, and custom base URL.
- Output-token defaults selected by OpenCode unless a supported public request field overrides them later.

Always replace/remove:

- Captured `messages` or `input`.
- Captured system/developer instructions.
- Captured tools/tool choice.
- Stream flags and stream options.
- Sentinel text and OpenCode-specific user/session metadata.
- Request IDs or cache keys derived from the burner where reuse would be incorrect.

Set the real upstream request to streaming regardless of public `stream`. The same event parser serves both public modes. Preserve only safe end-to-end headers; recompute `content-length` and remove the private marker and hop-by-hop headers.

Use the saved pre-wrapper fetch for the real request. This prevents recapture while retaining the final credentials and transformations already represented by the captured URL/headers/body. Link it to the external request abort signal and plugin shutdown signal.

## OpenAI Protocol Adapter

Add `src/proxy/openai.ts` with separate Chat and Responses implementations behind one adapter interface.

```ts
type ProviderEvent =
  | { type: 'text'; value: string }
  | { type: 'reasoning'; value: string }
  | { type: 'tool-start'; index: number; id: string; name: string }
  | { type: 'tool-arguments'; index: number; value: string }
  | { type: 'usage'; input: number; output: number; reasoning?: number }
  | { type: 'finish'; reason: 'stop' | 'length' | 'tool_calls' }
  | { type: 'error'; error: ProtocolError };
```

The exact type can be adjusted during implementation, but it must preserve tool index, ID, name, and incremental raw argument strings without schema validation.

### Chat request mapping

- Preserve OpenAI message roles and order.
- Convert normalized text and `image_url` parts back to Chat content parts.
- Preserve assistant `content: null` with `tool_calls`.
- Preserve historical parallel tool-call IDs, names, and raw argument strings.
- Emit tool messages with matching `tool_call_id` and content.
- Forward user function tools as native `type: 'function'` tools with name, optional description, and parameters.
- Do not execute tools and do not set a forced `tool_choice`.
- Validate URL/data images and limits before creating a burner; remote images remain pass-through.

### Responses request mapping

- Convert system/developer/user/assistant messages to Responses message/input items without collapsing role boundaries.
- Convert text parts to `input_text`/appropriate output text forms and image parts to `input_image` with URL/data URL.
- Convert historical assistant tool calls to `function_call` items using call IDs and raw arguments.
- Convert tool messages to `function_call_output` items correlated by `call_id`.
- Convert supplied functions to flat Responses function tool definitions.
- Keep the input sequence deterministic so a fresh request containing prior calls/results continues correctly.

### Upstream stream parsing

Chat parser:

- Incrementally parse SSE across arbitrary byte boundaries, comments, blank lines, multiple data lines, and `[DONE]`.
- Read `choices[0].delta.content`, explicit reasoning fields used by compatible providers, indexed parallel `tool_calls`, finish reason, usage, and provider error envelopes.
- Accumulate fragmented tool name/argument deltas without parsing or validating JSON arguments.

Responses parser:

- Handle response lifecycle, output item added/done, content part events, output text deltas, explicit reasoning summary/text deltas, function-call argument deltas/done, completion, incomplete, failed, and error events.
- Correlate output index/item ID/call ID so interleaved parallel function calls remain stable.
- Map incomplete token-limit status to `length`, function calls to `tool_calls`, and normal completion to `stop`.
- Map Responses usage, including explicit reasoning token details when present.

Both parsers must reject malformed terminal streams, non-2xx provider responses, HTML/non-JSON errors, missing terminal events, and unsupported multi-choice output using sanitized OpenAI error envelopes.

## Public Response Core

Refactor `src/openai/response.ts` and `src/openai/sse.ts` around `ProviderEvent`.

Streaming behavior:

- Generate one `chatcmpl-*` ID, timestamp, and requested public model ID before upstream execution.
- Emit an initial assistant-role chunk.
- Emit text and `reasoning_content` deltas in provider order.
- Emit tool call deltas with stable indices; include ID/type/name on first occurrence and argument fragments thereafter.
- Emit one final choice chunk with `stop`, `length`, or `tool_calls`.
- Emit usage as a final `choices: []` chunk when available.
- Emit `data: [DONE]` exactly once.
- After headers are sent, map failures to one sanitized SSE error frame followed by `[DONE]`, unless the client has cancelled.

Non-streaming behavior:

- Consume the identical event iterator.
- Concatenate text/reasoning and each tool call's raw argument fragments.
- Return all completed parallel calls in index order.
- Set `content: null` when there is no text, include `reasoning_content` only when explicit reasoning exists, and use `finish_reason: 'tool_calls'` whenever calls exist.
- Use the same IDs, finish mapping, usage mapping, timeout, and error normalization as streaming.

## Request Parsing and Validation

Retain the useful OpenAI parser/image validation but simplify it around proxy semantics.

- Validate `model`, non-empty `messages`, boolean `stream`, function tools, supported roles/content, tool-call history, and image forms before capture.
- Preserve generated/historical argument strings as opaque strings. Remove Ajv compilation, generated argument validation, retry budgets, and `422 tool_arguments_invalid` behavior.
- Permit parallel tool results in any order while requiring every tool message to reference a prior call.
- Permit a new continuation after all immediately preceding calls have results.
- Ignore explicitly deferred fields such as `tool_choice` and `response_format` for now, documenting that they are not forwarded.
- Keep body, image, tool count, schema size, request duration, and upstream response safety limits.
- Leave normalized types extensible for future `response_format` without coupling parsing to an adapter.

## Effective Models

Rework `src/opencode/client.ts` and `src/openai/models.ts` so model listing and resolution share one catalog calculation.

1. Read active project config through `client.config.get({ query: { directory } })`.
2. Read effective configured providers through `client.config.providers(...)`, not `/provider`'s complete catalog.
3. Apply `enabled_providers` and `disabled_providers` defensively even if OpenCode already filtered them.
4. Apply each provider's configured `whitelist` and `blacklist` to model IDs.
5. Include configured custom model entries and OpenCode-effective model overrides.
6. Exclude deprecated/disabled/unavailable entries according to fields exposed by the pinned SDK.
7. Filter to model metadata whose resolved API package/endpoint is known to use OpenAI Chat or Responses wire format.
8. Return canonical `provider/model` IDs and preserve additional slashes in model IDs.

Use the same catalog to resolve completion requests. `/v1/models` must never advertise a model that resolution rejects based on known metadata. Capture-time detection is a second guard: a custom or changed transport returns `unsupported_provider` and never performs the real inference request.

Add focused source investigation during implementation to confirm the pinned `config.providers` response already applies OpenCode's model status, whitelist/blacklist, and experimental-model rules. Keep any duplicate defensive filtering small and covered rather than reproducing OpenCode's whole provider resolver.

- Marked Chat and Responses requests resolve capture without invoking saved fetch.

- Headers work for `Headers`, tuples, objects, `Request`, and `RequestInit` forms.
- Marker stripping, duplicate capture rejection, timeout, cancellation, simultaneous requests, multiple plugin instances, and fetch restoration.
