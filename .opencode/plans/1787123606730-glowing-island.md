# Core Implementation Plan

## Architecture

Build a legacy OpenCode plugin that starts a separate Bun HTTP listener during plugin initialization and stops it from the plugin `dispose` hook. A plugin cannot add supported routes to OpenCode's existing listener, so the plugin will use the supplied `client`, `serverUrl`, `directory`, and `event` hook while owning `/v1/*` on a configurable second port.

Each Chat Completions request creates a burner OpenCode session, reconstructs the complete supplied conversation, runs one prompt, and always aborts/deletes the session. No conversation or tool result is retained after the request. Concurrent requests have isolated session IDs, tool registries, collectors, abort controllers, and timers.

Use one static plugin tool named `openai_tool_dispatcher` as a hybrid bridge for client-owned function tools:

- Deny the dispatcher by default in the plugin `config` hook, so normal TUI, desktop, and server sessions do not receive it in model tool definitions.
- For burner prompts, pass the tool map in insertion order as `{ '*': false, openai_tool_dispatcher: true }`, disabling all built-in, MCP, skill, and other plugin tools while enabling only the dispatcher.
- Gate dispatcher execution with an in-memory allowlist of active burner session IDs. Reject every non-burner invocation even if another client explicitly enables the tool.
- Inject each request's external function names, descriptions, schemas, prior assistant tool calls, and tool results into a strict JSON transcript/system protocol. Dynamic schemas cannot be registered natively per session.
- Have the model call the dispatcher with `{ name, arguments }`. The dispatcher validates the external name and arguments, captures valid calls, and never executes an external function.
- Return all calls captured during a bounded parallel-call collection window as OpenAI `tool_calls`. The caller executes them and supplies assistant `tool_calls` plus `tool` messages in its next complete, stateless request.

The dispatcher may remain visible in OpenCode's internal/experimental tool catalog because registration is instance-wide; document this accepted limitation.

### Component topology

```text
OpenAI-compatible client
        |
        | HTTP/SSE on configured loopback port
        v
+---------------------------- plugin process -----------------------------+
| Bun HTTP listener                                                     |
|   -> auth/CORS/router                                                  |
|   -> request parser                                                    |
|   -> model catalog                                                     |
|   -> SessionRunner ------------------------------------------------+   |
|        |                                                          |   |
|        | registers BurnerContext                                  |   |
|        v                                                          |   |
|   DispatcherRegistry <---- static openai_tool_dispatcher          |   |
|        ^                       (plugin tool hooks)                  |   |
|        |                                                          |   |
|   EventHub <-------------------- plugin event hook                 |   |
|        |                                                          |   |
|        +---- text/reasoning/status/error events ------------------+   |
|                                                                       |
+-----------------------------------------------------------------------+
         | OpenCode SDK client supplied in PluginInput
         v
OpenCode server
  -> create burner session
  -> prompt with only dispatcher enabled
  -> abort/delete burner session
  -> provider/model inference
```

Ownership rules:

- `plugin.ts` owns process-lifetime resources: options, HTTP listener, model service, event hub, dispatcher registry, active request set, and disposal.
- `SessionRunner` owns request-lifetime resources: session, transcript, compiled tool schemas, collector, event consumer, timeout, abort signal, accumulated output, and cleanup.
- `DispatcherRegistry` owns only active burner lookup/call correlation. It never owns conversation history or persists user schemas after cleanup.
- The HTTP layer owns protocol concerns and never calls OpenCode session methods directly.
- OpenCode adapters own SDK shape differences and never construct OpenAI JSON/SSE directly.
- Response mappers are pure functions over normalized completion state, making stream and non-stream behavior testable without an OpenCode server.

### Dependency direction

Keep dependencies one-way to avoid hook/HTTP cycles:

```text
index -> plugin -> http router -> chat service -> session runner -> OpenCode client
                  |               |                 |
                  |               v                 v
                  |            transcript       event hub
                  |               |
                  v               v
              OpenAI types <- completion result <- dispatcher collector
```

`plugin.ts` performs dependency injection through small structural interfaces rather than making modules import mutable singletons. The dispatcher tool closes over the one `DispatcherRegistry` instance created by the plugin. Tests substitute fake clients, clocks, UUID generation, and event delivery without monkey-patching global state.

### Core internal contracts

Use explicit interfaces equivalent to the following; exact SDK response aliases can be refined during implementation:

```ts
type BurnerContext = {
  requestID: string;
  sessionID: string;
  tools: RequestToolRegistry;
  collector: ToolCallCollector;
  callIDs: CallIDCorrelator;
  signal: AbortSignal;
};

type NormalizedCompletion = {
  id: string;
  created: number;
  model: string;
  text: string;
  reasoning: string;
  toolCalls: CapturedToolCall[];
  finishReason: 'stop' | 'length' | 'tool_calls';
  usage?: NormalizedUsage;
};

interface OpenCodeSessionClient {
  createSession(signal: AbortSignal): Promise<{ id: string }>;
  prompt(input: BurnerPrompt, signal: AbortSignal): Promise<OpenCodePromptResult>;
  abortSession(sessionID: string): Promise<void>;
  deleteSession(sessionID: string): Promise<void>;
}

interface SessionEventConsumer {
  onEvent(event: OpenCodeEvent): void;
  close(error?: Error): void;
}
```

Wrap the generated SDK client behind `OpenCodeSessionClient` in `src/opencode/client.ts`. This local adapter centralizes `query.directory`, `path.id`, `throwOnError`, SDK response unwrapping, unknown error conversion, and version-specific field access so protocol modules do not depend on generated SDK details.

### Process lifecycle

Plugin initialization order must be deterministic:

1. Parse options and reject insecure/invalid configuration.
2. Probe OpenCode health/version and required client capabilities.
3. Create the dispatcher registry and event hub.
4. Construct the static dispatcher tool over that registry.
5. Construct HTTP dependencies and bind `Bun.serve`.
6. Add the listener to process-lifetime state.
7. Return hooks only after successful binding.

If any initialization step fails, close already-created resources before rejecting plugin setup. Do not leave a partial listener running.

Plugin disposal order:

1. Mark the service as draining so new HTTP requests receive `503`.
2. Stop accepting new connections.
3. Abort active request controllers.
4. Await bounded request cleanup.
5. Force-close the Bun listener if the grace period expires.
6. Clear dispatcher/event registries and timers.

Make `dispose` idempotent because OpenCode shutdown and failed startup cleanup may both call it.

### Request lifecycle

Every chat request follows the same state machine:

```text
received
  -> authenticated
  -> parsed
  -> model_resolved
  -> session_created
  -> registered
  -> prompting
       -> completed_text
       -> collecting_tools -> aborting_after_capture
       -> failed
       -> client_cancelled
       -> timed_out
  -> finalized
  -> deleting_session
  -> closed
```

Only transition to `prompting` after the session is registered in both `EventHub` and `DispatcherRegistry`; this prevents losing an immediate model event or tool invocation. Only emit a successful final OpenAI response after completion state is finalized. Session deletion occurs for every terminal state, including body-stream cancellation after HTTP headers have been sent.

The runner returns a discriminated result rather than throwing for expected outcomes:

```ts
type RunOutcome =
  | { type: 'completion'; completion: NormalizedCompletion }
  | { type: 'tool_calls'; completion: NormalizedCompletion }
  | { type: 'cancelled' };
```

Validation, model, auth, timeout, and upstream failures use typed internal errors that the HTTP boundary maps to OpenAI error envelopes.

### Isolation invariants

The implementation must preserve all of these invariants:

- A session is added to the dispatcher allowlist only after this server creates it and is removed before request resources are released.
- An allowlist entry stores the exact immutable request tool registry; no global "current request" or "current schema" variable is allowed.
- A normal OpenCode session receives the config-level dispatcher deny and no request registry.
- An unauthorized dispatcher invocation fails before examining its arguments or revealing any user tool definition.
- The burner prompt enables no tool except `openai_tool_dispatcher`; tests inspect the exact prompt payload and effective real-server tool set.
- Captured calls from one session cannot be read, reset, or completed by another session.
- Session IDs, call IDs, and request IDs are opaque correlation values, not authorization values supplied by the OpenAI client.
- Deleting a burner session and clearing its registry entry are mandatory even if the HTTP client disconnects or OpenCode abort/delete calls fail.

## Source Structure

### Plugin and lifecycle

- Replace `src/index.ts` with the package entrypoint exporting the OpenCode `PluginModule` (`server`), the plugin function, option/public protocol types, and plugin version.
- Add `src/plugin.ts` to validate options, perform startup capability checks, create shared coordinators, start `Bun.serve`, return `config`, `event`, `tool`, `tool.execute.before`, `tool.execute.after`, and `dispose` hooks, and fail initialization if the HTTP listener cannot start.
- Add `src/config.ts` with strict plugin tuple option parsing:
  - `host?: string`, default `127.0.0.1`.
  - `port?: number`, default a documented fixed port such as `4097`; allow `0` for tests.
  - `cors?: boolean | string[]`, default `false`; `true` means wildcard origins and an array is an exact allowlist.
  - `token?: string`; use `Authorization: Bearer <token>`. Require a non-empty token when binding outside loopback, while allowing tokenless loopback use.
  - Reject unknown keys and invalid values. Configuration comes only from the official `plugin: [[name, options]]` OpenCode config form, with no environment fallback.
- Add `src/version.ts` for `PLUGIN_VERSION`, kept equal to `package.json` without introducing release-workflow changes.
- Add `src/opencode/capabilities.ts` to call `${serverUrl}/global/health`, cache the OpenCode version, and verify required client methods and supported OpenCode API behavior before serving requests. Capability-check the intended OpenCode version range rather than assuming private internals.
- Add `src/opencode/client.ts` as the generated-SDK isolation layer described above; use the plugin-provided client instead of creating a second client or mutating global OpenCode config through `client.config.update`.

### HTTP and OpenAI protocol

- Add `src/http/server.ts`, `src/http/router.ts`, `src/http/auth.ts`, and `src/http/cors.ts` around a testable Fetch-style handler and a thin `Bun.serve` lifecycle wrapper.
- Implement:
  - `POST /v1/chat/completions`.
  - `GET /v1/models`.
  - `GET /version`, returning `{ plugin, opencode }` versions.
  - CORS `OPTIONS` handling and OpenAI-shaped `404`/`405` errors.
- Authenticate `/v1/*` and `/version` when a token is configured. Accept only a bearer header, do not log secrets, allow preflight without auth, and return `WWW-Authenticate: Bearer` with OpenAI-shaped `401` errors.
- Add `src/openai/types.ts` and `src/openai/parse.ts` with explicit types and runtime validation for the supported Chat Completions surface:
  - `model`, `messages`, `tools`, and `stream`.
  - `system`, `developer`, `user`, `assistant`, and `tool` roles.
  - String content and ordered `text`/`image_url` content parts.
  - Assistant `tool_calls` and tool messages with `tool_call_id`.
  - Function tools with unique names, optional descriptions, and JSON Schema parameters.
  - Validate malformed supported fields and tool history, but ignore unrelated/unsupported Chat Completions fields, including `tool_choice`, sampling controls, `response_format`, and structured-output options.
- Add `src/errors.ts` for sanitized OpenAI error envelopes and status mappings: invalid request/schema/image/model (`400`), auth (`401`), body too large (`413`), repeated invalid generated arguments (`422`), OpenCode/provider failure (`502`/`503`), timeout (`504`), and internal errors (`500`).
- Enforce bounded request body, tool count, schema size, image data size, transcript size, generated call count, and request duration limits as named constants with documented values.

Implement routing as exact method/path matches. Read and validate the request body before creating a burner session. Build all JSON responses through a `jsonResponse` helper so content type, CORS, request ID, and error formatting remain consistent. Generate one internal request ID for logs/correlation and one stable `chatcmpl-*` ID for all response chunks.

The initial compatibility contract should intentionally support one choice (`choices[0]`) even if the request contains `n`; because unsupported fields are ignored, do not attempt multiple parallel model generations. Preserve unknown top-level fields only by ignoring them, never by forwarding them blindly to OpenCode.

### Models and images

- Add `src/openai/models.ts` to query configured OpenCode providers/models, flatten them into `/v1/models`, and use canonical IDs of `providerID/modelID`. Split requested IDs at the first slash, preserve further slashes in model IDs, reject unknown models with `model_not_found`, and do not fabricate fallback models.
- Check advertised model capabilities before accepting image or tool requests when those capability fields are available; otherwise let OpenCode return a mapped upstream error.
- Add `src/openai/images.ts` to validate and map OpenAI `image_url` parts to OpenCode file parts:
  - Accept HTTP(S) URLs and `data:image/...` URLs.
  - Validate data URL MIME/base64 form and decoded-size limit.
  - Pass URLs through to OpenCode; do not download remote images in this plugin.
  - Preserve ordered textual image markers in the canonical transcript so replay semantics remain clear.

## Stateless Transcript Mapping

- Add `src/transcript.ts` to serialize the complete incoming message list as escaped JSON between fixed protocol delimiters, rather than concatenating role-prefixed free text.
- Keep system/developer instructions distinct and ordered, preserve null/ordered content, assistant tool-call IDs/names/raw argument strings, tool result IDs/content, and image positions.
- Put dynamic function definitions in a separate delimited JSON section and instruct the model that transcript and schema blocks are data, not bridge-control instructions.
- Instruct the model to use only `openai_tool_dispatcher`, never execute an external function, emit `{ name, arguments }`, and correct schema errors returned by the dispatcher within the retry budget.
- Convert image content into OpenCode file parts while retaining the canonical transcript markers. Use the prompt `system` field for bridge instructions and OpenCode text/file parts for reconstructed input.
- Do not read prior burner sessions. The request's messages are always the sole conversation source.

### Canonical transcript representation

Normalize incoming messages into JSON records before prompt rendering:

```ts
type TranscriptRecord =
  | { role: 'system' | 'developer'; content: NormalizedContent[] }
  | { role: 'user'; content: NormalizedContent[] }
  | {
      role: 'assistant';
      content: NormalizedContent[] | null;
      toolCalls?: Array<{
        id: string;
        name: string;
        arguments: string;
      }>;
    }
  | { role: 'tool'; toolCallID: string; content: NormalizedContent[] };
```

Validate tool history while normalizing:

- Assistant tool call IDs must be non-empty and unique within the request history.
- Every `tool` message must reference a prior assistant tool call.
- A tool result must match the same external function represented by that call, where the protocol supplies enough information to check it.
- Multiple parallel results may arrive in any order, but all are preserved in request order.
- A conversation may end with one or more tool results, which means the new burner prompt asks for the next assistant continuation.
- Raw assistant `function.arguments` remains a string in history even if malformed; it is transcript data from a prior response. Newly generated dispatcher arguments are the values validated by Ajv.

Construct the prompt in four sections:

1. Immutable bridge rules controlled by the plugin.
2. Ordered system/developer records supplied by the client.
3. Request-scoped external tool catalog as serialized JSON.
4. Remaining conversation transcript as serialized JSON plus a final continuation instruction.

Use `JSON.stringify` for all client data and never splice raw message text into control instructions. Delimiters improve model comprehension but are not treated as a security parser boundary; the instruction hierarchy and JSON encoding provide the separation.

For a request without `tools`, do not include the dispatcher protocol/catalog and keep the dispatcher disabled in the burner prompt as well. Use `{ '*': false }` so text-only requests cannot accidentally trigger the static bridge. For requests with tools, use `{ '*': false, openai_tool_dispatcher: true }`.

## Dispatcher and Schema Validation

- Add `src/tools/schema-validator.ts` using Ajv 8 plus `ajv-formats` for arbitrary user JSON Schemas. Compile schemas before session creation, support common OpenAI draft-07 schemas and declared newer drafts where Ajv supports them, reject invalid/unresolved schemas, and disable coercion, defaults, property removal, and input mutation.
- Add `src/tools/registry.ts` for an immutable request-scoped map from external tool name to definition and compiled validator. Remove the map during request cleanup and never expose it to ordinary sessions.
- Add `src/tools/dispatcher.ts` defining the one broad static OpenCode tool and coordinating these hooks:
  - Capture the OpenCode `callID` in `tool.execute.before`, since the pinned `ToolContext` exposes session/message IDs but not `callID` in its public type.
  - In `execute`, require an allowlisted session, correlate the call ID, verify the external name, and validate `arguments` against that exact request schema.
  - On invalid name/arguments, return a short synthetic tool error containing sanitized Ajv paths/messages so the model can correct itself. Count the attempt and do not expose it as an OpenAI call.
  - On a valid call, record the external name, arguments, OpenCode call ID, message ID, and arrival order; return immediately with a synthetic "captured, do not execute" result so plugin execution never waits indefinitely.
  - Deduplicate by call ID and clear hook correlation state in `tool.execute.after`/request cleanup.
- Validation is intentionally stronger than baseline OpenAI behavior: OpenAI warns callers that generated arguments may be invalid, but this bridge will return only schema-valid calls. After a bounded number (initially three) of invalid attempts with no valid call, abort and return `422 tool_arguments_invalid`.
- Add `src/tools/collector.ts` for best-effort parallel capture. After the first valid call, reset a short quiet timer when each additional call arrives, enforce a hard collection deadline and maximum call count, then abort the OpenCode session. Preserve stable arrival-order indices and return every validated call captured before closing. Keep timing values centralized and cover them with fake timers.

### Dispatcher coordination details

Use these maps inside one `DispatcherRegistry` instance:

```ts
Map<sessionID, BurnerContext>
Map<sessionID, Map<callID, PendingHookCall>>
```

`tool.execute.before` records `{ callID, args, arrivalSequence }` before `execute` runs. Because `ToolContext` lacks a typed call ID in the pinned package, `execute` correlates the oldest unclaimed pending hook call for the same session whose normalized arguments match. Mark it claimed atomically in synchronous map operations before awaiting validation/capture work. If correlation is ambiguous or missing, fail closed and return no external call.

Prefer dispatcher arguments as an object:

```json
{
  "name": "external_function_name",
  "arguments": {
    "field": "value"
  }
}
```

The static plugin tool uses a broad Zod envelope (`name` string and `arguments` unknown/object) only to enter `execute`; Ajv validates the full external function schema. If a model supplies `arguments` as a JSON string, parse it once only if it contains a JSON object, then validate the parsed value. Preserve one canonical JSON string generated from the validated value in the OpenAI response.

Validation/correction flow:

```text
dispatcher invoked
  -> session allowlisted?
  -> external name exists?
  -> arguments normalize to JSON value?
  -> Ajv schema passes?
       yes -> capture/deduplicate -> notify collector -> synthetic captured result
       no  -> count invalid attempt -> bounded validation feedback to model
                 -> attempts remain: model may call dispatcher again
                 -> exhausted: signal runner to abort and return 422 if no valid calls
```

Do not expose complete schemas or submitted arguments in validation errors. Return only tool name, JSON pointer, failed keyword, and concise message. Cap the number and serialized length of Ajv errors sent back to the model.

Tool-call IDs returned to the OpenAI client should preserve the OpenCode call ID after making it safe for the OpenAI wire format, for example `call_<opaque-id>`. Maintain a map so retries/deduplication return a stable ID. Do not trust or reuse historical client call IDs for newly generated calls.

### Collector state machine

```text
open
  -> first valid call -> collecting
  -> invalid budget exhausted with no valid calls -> invalid_exhausted
collecting
  -> another valid call -> collecting (reset quiet timer)
  -> quiet timer -> closing
  -> hard deadline/max count -> closing
closing
  -> request session abort -> closed
```

Start the hard collection deadline with the first valid call, not at HTTP request start. Request timeout remains an independent outer deadline. Calls accepted before `closing` are immutable snapshots. Invalid retries after at least one valid call do not discard valid calls; final output contains validated calls collected before closure.

Because OpenCode may begin executing parallel tools independently, returning a synthetic result is used only to avoid hanging tool execution. The runner's abort after the collection boundary is what stops the agent loop. This is best-effort and must be measured in the real smoke test.

## Session Execution and Streaming

- Add `src/opencode/event-hub.ts` that receives events through the plugin's existing `event` hook and routes only allowlisted session events to per-request consumers. Do not open a redundant SDK global SSE subscription.
- Correlate `message.part.updated`, `message.updated`, `session.status`, `session.idle`, and `session.error` by session/message/part IDs. Track cumulative part text to avoid duplicate deltas.
- Add `src/opencode/session-runner.ts` shared by streaming and non-streaming routes:
  1. Resolve model and compile request tools.
  2. Create a burner session.
  3. Register it in the dispatcher allowlist/event hub before prompting.
  4. Prompt with the resolved provider/model, reconstructed system/parts, and `{ '*': false, openai_tool_dispatcher: true }`.
  5. Collect direct response data and/or event deltas while the dispatcher collector can trigger a bounded abort.
  6. Reconcile final text, reasoning, tool calls, token usage, and finish status without duplicating streamed output.
  7. In `finally`, stop timers, unregister all maps/listeners, abort unfinished work, and delete the session. Use bounded cleanup and `Promise.allSettled` so abort failure never prevents delete.
- Link client disconnect and request timeout to an `AbortController`; stop writing immediately after disconnect and abort/delete the burner session.
- Do not serialize unrelated requests globally.
- Add `src/openai/response.ts` to map final results:
  - Text to `message.content`.
  - Visible OpenCode reasoning to the documented nonstandard `message.reasoning_content`.
  - Valid captured calls to `message.tool_calls` with `finish_reason: 'tool_calls'` and JSON-stringified arguments.
  - Normal completion to `stop`, output limit to `length`, and OpenCode token counters to OpenAI usage fields, including reasoning-token details when available.
- Add `src/openai/sse.ts` to emit stable completion ID/timestamp/model values, an initial assistant-role chunk, text and `reasoning_content` deltas, indexed tool-call chunks, a final finish/usage chunk, and `data: [DONE]`. Once SSE headers are sent, map later failures to a sanitized SSE error/close path rather than attempting a JSON HTTP error.

### Prompt execution strategy

Use the synchronous `client.session.prompt` operation for both modes while events arrive independently through the plugin hook:

- Non-streaming awaits the direct prompt result, unless the collector asks the runner to abort after capturing tools.
- Streaming starts the prompt promise without awaiting it immediately, consumes event callbacks into the SSE `ReadableStream`, and reconciles with the prompt result before the final chunk.
- The runner treats the expected abort caused by validated tool capture as control flow, not an upstream failure.
- An abort before any validated call remains a cancellation/timeout/error according to its initiating signal.

If the synchronous SDK call cannot be aborted with a request signal in the pinned client, race it with the runner signal but still call `session.abort`; keep the unresolved promise observed so rejection cannot become unhandled. Confirm the generated SDK method's signal option during implementation and isolate any cast inside `src/opencode/client.ts`.

### Event accumulator

Maintain per assistant part:

```ts
type PartAccumulator = {
  type: 'text' | 'reasoning';
  value: string;
  emittedLength: number;
};
```

For each `message.part.updated` event:

- Ignore non-burner sessions and non-assistant messages.
- If `delta` is present, append it unless the accompanying cumulative part proves it is duplicated.
- If only cumulative text is present and it starts with the stored value, derive the suffix.
- If event history is inconsistent, retain the longest coherent value and defer correction to final reconciliation rather than emitting replacement text.
- Stream only newly derived suffixes.

Use `message.updated` for final message metadata, token counts, provider finish reason, and assistant message ID. Use `session.error` as terminal failure. Use `session.idle` only as a completion signal after the direct prompt result/message state has been reconciled; idle alone does not prove the finish reason.

### SSE sequencing

Emit chunks in this order:

1. Assistant role chunk with empty delta content omitted.
2. Zero or more `reasoning_content` and `content` delta chunks in event order.
3. Tool call chunks, if captured. Because dispatcher capture exposes complete validated arguments, emit one complete tool-call delta per index rather than inventing token-level argument deltas.
4. Final choice chunk with empty `delta` and `finish_reason`.
5. Final usage chunk with `choices: []` when usage is known.
6. `data: [DONE]`.

For tool completions, do not stream synthetic dispatcher result text as assistant content. Filter text generated after the first validated dispatcher call unless it clearly predates the tool-call event; final `finish_reason` is `tool_calls`. Preserve reasoning emitted before collection as `reasoning_content`.

When a post-header stream error occurs, emit a final OpenAI-shaped error object as an SSE `data:` frame and then `[DONE]`, provided the client is still connected. Do not emit a successful finish chunk.

### Cleanup algorithm

Implement one idempotent `cleanup()` closure per request:

```text
mark runner closed
-> cancel request/collector timers
-> stop event delivery and SSE enqueueing
-> remove dispatcher allowlist and pending call correlations
-> if prompt may still run, request session abort
-> always request session delete
-> await both with a bounded cleanup timeout
-> remove request from plugin active-request set
```

Remove the allowlist before awaiting network cleanup so no late dispatcher invocation is authorized. Preserve the session ID locally until delete finishes. Cleanup failures are logged with request/session IDs but do not replace an already completed client response.

## Implementation Decisions and Edge Cases

- **Configuration merge:** the `config` hook must preserve existing tool and permission settings while appending an exact dispatcher deny. Do not replace the user's complete `tools` or `permission` objects. Add a unit test for pre-existing entries and a real test for effective model visibility.
- **No request tools:** do not enable or mention the dispatcher; use wildcard deny only.
- **Empty tools array:** normalize it to no request tools.
- **Tool name collision:** external names may equal built-in names because only the dispatcher is registered/enabled. External names must still be unique within the request catalog.
- **Dispatcher name collision:** reserve `openai_tool_dispatcher` as an internal name; an external function may use that string because it is data inside the dispatcher catalog, but document that generated diagnostics distinguish internal and external names.
- **Assistant text plus calls:** preserve text emitted before valid calls in non-stream output if it is coherent, but finish with `tool_calls`; avoid synthetic post-call text.
- **Partial parallel results in next request:** preserve what the client sends but reject a continuation when a new assistant turn occurs before all immediately preceding parallel calls have matching tool results. This avoids ambiguous tool history.
- **Malformed historical arguments:** preserve them as opaque prior transcript strings. Validate only newly generated dispatcher arguments; do not rewrite client history.
- **Duplicate historical call IDs:** reject with `400` because tool results could not be correlated deterministically.
- **Provider emits native tool events unexpectedly:** treat this as an isolation failure/upstream error because only the dispatcher should be enabled; do not expose an unvalidated native call.
- **No assistant output:** return `content: null` with `stop` only when OpenCode completed successfully; otherwise map the terminal error.
- **Unknown OpenCode part types:** ignore non-user-visible lifecycle parts, but fail safely if an unknown part claims to be an executable tool event.
- **Reasoning privacy:** expose only explicit OpenCode reasoning parts, never infer hidden reasoning or include internal bridge/validation diagnostics.
- **Usage unavailable:** omit usage fields rather than fabricate zero values. Keep usage mapping identical between stream and non-stream finalization.
- **Remote image URL:** pass through without fetching; the downstream provider/OpenCode owns retrieval. Validate only scheme/shape and model capability.
- **Data URL:** reject malformed/oversized payloads before creating a burner session and avoid logging the encoded data.
- **Port collision:** fail plugin initialization with actionable context; do not search for another port except when the user explicitly configures port `0`.
- **Multiple plugin instances:** each instance owns a listener and registries. A configured port collision fails the later instance; there is no process-global singleton.
- **OpenCode event ordering:** tolerate event-before-prompt-resolution and prompt-resolution-before-final-event. Registration occurs before prompt, and finalization reconciles both sources.
- **Cleanup race:** late hooks/events after registry removal are ignored/rejected. Cleanup remains idempotent and never re-authorizes a session.
- **Server draining:** in-flight requests may finish within the grace period, but disposal aborts them after the deadline and always attempts session deletion.
